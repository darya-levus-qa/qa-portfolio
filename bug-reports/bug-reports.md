# Баг-репорты

Примеры из коммерческой работы на проекте Hub-PM (WebSocket API). Все данные обезличены: email, имена, Id и внутренние названия заменены на условные.

## Пример 1. Функциональный баг: фильтр по роли не применяется

**Заголовок:** Main Ws / PerformersListService / GetOwnedDetailUsers - фильтрация по полю Role не применяется для значений 0 (Employee) и 1 (NamespaceAdmin)

**Предусловия**

1. Пользователь авторизован под владельцем
2. Есть проект с сотрудниками
3. В проекте есть администратор проекта и сотрудник без прав администратора

**Описание**

При отправке запроса на метод Main Ws / PerformersListService / GetOwnedDetailUsers фильтрация по полю Role работает только для значения 2 (ProjectAdmin): у пользователя, который не является администратором проекта, список проектов приходит пустым. Для значений 0 (Employee) и 1 (NamespaceAdmin) фильтрация не применяется:

1. Role = 0 (Employee), в поиске администратор проекта - проект возвращается, хотя пользователь не обычный сотрудник
2. Role = 1 (NamespaceAdmin), в поиске сотрудник без прав администратора рабочей области - проект возвращается
3. Role = 2 (ProjectAdmin), в поиске сотрудник без прав администратора проекта - список проектов пустой, фильтр работает

**Шаги воспроизведения**

1. Отправить запрос на метод Main Ws / PerformersListService / GetOwnedDetailUsers, указав Role = 0 и в поле Search фамилию администратора проекта
2. Отправить запрос на тот же метод, указав Role = 1 и в поле Search фамилию сотрудника без прав администратора рабочей области
3. Отправить запрос на тот же метод, указав Role = 2 и в поле Search фамилию сотрудника без прав администратора проекта

**Фактический результат**

После запросов с Role = 0 и Role = 1 проект возвращается у пользователей, которые не соответствуют роли. После запроса с Role = 2 список проектов пустой.

**Ожидаемый результат**

Метод Main Ws / PerformersListService / GetOwnedDetailUsers возвращает только проекты, в которых пользователь имеет роль из поля Role, для всех значений перечисления

**Приложения:** аккаунт, под которым воспроизводится, ответы на все три запроса

## Пример 2. Ошибка метода: 500 вместо ошибки валидации

**Заголовок:** Main Ws / EmployeeService / UpdateEmployeeForManager - при несуществующем UserId возвращается ошибка 500 вместо ошибки валидации

**Предусловия**

1. Пользователь авторизован в системе
2. Есть сотрудник в рабочей области

**Описание**

При отправке запроса на метод Main Ws / EmployeeService / UpdateEmployeeForManager с несуществующим значением в поле UserId метод не проверяет существование пользователя и падает на уровне базы данных - возвращается код 500 и текст исключения DbUpdateException с нарушением внешнего ключа. Для остальных некорректных значений поля (0, отрицательное, дробное, максимум и минимум Int64, пустое, Null) метод возвращает корректную ошибку валидации.

**Шаги воспроизведения**

1. Отправить запрос на метод Main Ws / EmployeeService / UpdateEmployeeForManager, указав в поле UserId несуществующий Id

**Фактический результат**

Возвращается ошибка с кодом 500 и текстом исключения базы данных DbUpdateException

**Ожидаемый результат**

Метод Main Ws / EmployeeService / UpdateEmployeeForManager возвращает ошибку валидации

**Приложения:** аккаунт, под которым воспроизводится

## Пример 3. Права доступа: пользователь без доступа получает данные рабочей области

**Заголовок:** Main Ws / NamespacePriorityService / GetList, GetListDetail - пользователь без доступа к рабочей области получает ее приоритеты

**Предусловия**

1. Пользователь авторизован
2. Пользователь не является участником проекта и рабочей области
3. В рабочей области настроены приоритеты

**Описание**

Методы Main Ws / NamespacePriorityService / GetList и Main Ws / NamespacePriorityService / GetListDetail возвращают приоритеты рабочей области пользователю, у которого нет доступа к этой рабочей области. Проверка доступа к рабочей области в методах не работает:

1. GetList под пользователем без доступа - успех, приоритеты рабочей области возвращаются
2. GetListDetail под пользователем без доступа - успех, приоритеты рабочей области возвращаются

**Шаги воспроизведения**

1. Отправить запрос на метод Main Ws / NamespacePriorityService / GetList под пользователем без доступа, указав Id рабочей области
2. Отправить запрос на метод Main Ws / NamespacePriorityService / GetListDetail под тем же пользователем, указав Id той же рабочей области

**Фактический результат**

Оба метода возвращают успех (IsSuccess: true) и приоритеты рабочей области

**Ожидаемый результат**

Методы Main Ws / NamespacePriorityService / GetList и Main Ws / NamespacePriorityService / GetListDetail возвращают ошибку доступа, приоритеты
